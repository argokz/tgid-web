# Возможности ИИ в веб-ТГИД

Дата: 23.10.2026. Основание: исследование itwin-api, web-itwin, схемы БД (`sety/1/full_tgid.sql`), эталонов gid6/gid8 и документов `desktop-web-migration-audit.md`, `qa-2026-09-30.md`, `sety/REVIEW_2026-10-18.md`.

Решения пользователя: облачная LLM (Claude API); приоритетные направления — расчёты и наладка, ТУ и подключение, износ и ремонты, качество данных и поиск; сначала прогон существующих проверок, затем внедрение по этапам. План — `~/.claude/plans/iterative-riding-sifakis.md`.

## 1. Исходное состояние

- ИИ, ML и LLM в коде нет (grep по `openai|anthropic|llm|sklearn|torch|embedding` в обоих репо — ноль). Из «умных» точек есть только словарь синонимов для сопоставления колонок импорта (`database/network_import.suggest_mapping`), подбор стандартного диаметра шайбы (`database/throttling_calc.recommended_standard_diameter`), пороги «рекомендуемых» скоростей и удельных потерь (`sql/admissibility/10.sql`) и жадное достраивание графа в паспорте (`passport_module/graph2.py`).
- Данные для машинного обучения на истории **отсутствуют**: в `almatygid` журналы повреждений (`defect`), ремонтов (`remont2`), шурфов, осмотров, опрессовок и все таблицы результатов расчёта `*_out` пусты. Реальные объёмы есть только в паспортах труб (`heatpipesections` ~98 тыс. строк, ~200 полей), потребителях (~52 тыс.), ТУ (4 775), АЛСЕКО (30 511 договоров, 187 тыс. зданий), температурных графиках (5 250).
- Поэтому первый слой ИИ — не обучаемые модели, а **детерминированные расчёты + LLM** для объяснений, ранжирования и разбора свободного текста. ML на истории — после накопления журналов (или загрузки старых `defekt2`/`capital2`, если найдутся в других городах).

## 2. Принципы встраивания

| Принцип | Как реализуется |
|---|---|
| LLM только на сервере | Веб вызывает `/api/v1/ai/*`; ключ `ANTHROPIC_API_KEY` в `.env` API; флаг `AI_ENABLED` (по умолчанию выключен) отдаётся через `/auth/config`, кнопки в вебе скрыты без него |
| Минимум данных наружу | В запрос уходят только нужные записи (протокол расчёта, агрегаты, отфильтрованные строки). Пароли, хэши, данные пользователей — никогда |
| Числа считает код, слова — LLM | Баланс, износ, кандидаты подключения, аномалии — SQL/Python. LLM объясняет, ранжирует неоднозначное, разбирает свободный текст |
| Структурированные ответы | Только JSON-схема (`output_config.format`) или pydantic-модель; «сырой» текст в логику не попадает |
| Учёт расходов | Каждый вызов — запись `ai_request` в `activity_log` (кто, инструмент, токены) |
| Модель | `claude-opus-5-5` по умолчанию (`AI_MODEL`), адаптивное мышление, `effort` medium для разбора, high для объяснений |

## 3. Карта модулей: где ИИ полезен

Тип: **LLM** — языковая модель; **АЛГ** — детерминированный алгоритм/SQL без ИИ; **ML** — обучаемая модель (позже, когда появится история). Готовность данных: ✅ есть, ⚠️ частично, ❌ нет. Приоритет: П1 — этапы 3–6 плана; П2 — после них; П3 — отложено.

## 4. Архитектура приоритетных направлений (этапы 2–6 плана)

```
web-itwin                      itwin-api                         Anthropic
AiAnswerPanel.vue  ──HTTP──►  routers/ai.py ──► ai/client.py ──► Claude API
(объекты → карта)             │   (AI_ENABLED, лимиты, activity_log)
                              ├─ database/calc_protocols.py  (этап 3)
                              ├─ database/tu_connection.py   (этап 4)
                              ├─ database/wear.py            (этап 5)
                              └─ database/data_quality.py    (этап 6)
```

- `ai/client.py` — ленивый `AsyncAnthropic`, конфиг из env, ошибки SDK → 502/503 с кодом без текста исключения.
- `ai/prompts/` — системные промпты файлами со стабильным префиксом (кеш промпта).
- `ai/schemas.py` — pydantic-модели ответов; все вызовы через `output_config.format`.
- Миграции схемы (колонка `calculation_protocol.ai_summary`, таблицы `data_quality_issue`, `iznos`/`calculation_iznos` при отсутствии) — пункты `database/city_schema.py`, без ручных скриптов.

## 5. Отложено (П3) и почему

- **Прогноз повреждаемости (ML)** — нет истории в `defect`/`remont2`; начать можно после года ведения журналов или импорта старых таблиц из других городов.
- **Глобальная оптимизация шайб/элеваторов и подбор диаметров** — требует многократных прогонов sety (минуты на фрагмент) и сверки с десктопом; сначала нужны юнит-тесты движка (этап 1).
- **Локальные модели (Ollama)** — отклонено пользователем в пользу облака.
- **Чат по отчётам и журналам** — после рефакторинга журналов F64/F65, чтобы фильтры были едиными.

## 7. Оценка расходов на LLM

Оценка по размеру входа (токенов на вызов, Opus 5.5: $4 вход / $20 выход за 1 млн):

| Инструмент | Вход, ток. | Выход, ток. | ≈ $/вызов | Частота | ≈ $/мес |
|---|---|---|---|---|---|
| Объяснение протокола расчёта | 6 000 | 1 500 | 0,05 | 50 расчётов/мес | 3 |
| Рекомендации по регуляторам | 4 000 | 1 000 | 0,04 | 30 | 1 |
| ТУ: разбор заявки + выбор точки | 5 000 | 1 500 | 0,05 | 100 заявок/мес | 5 |
| Записка к плану ремонтов | 8 000 | 3 000 | 0,09 | 5 | 0,5 |
| Сводка по качеству данных | 6 000 | 1 500 | 0,05 | 20 | 1 |
| Поиск фразой | 1 500 | 300 | 0,01 | 500 | 6 |
| Сопоставление колонок импорта | 2 000 | 500 | 0,02 | 20 | 0,4 |

Итого порядка 15–20 $/мес на город при указанной нагрузке; кеш системных промптов снижает вход ещё примерно на треть. Фактические токены видны в `activity_log`.
