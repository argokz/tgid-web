# Этап B — Редактор топологии сети (план)

Дата: 2026-07-24. Статус: B1/B2 реализованы в коде (за флагом), приёмка на стенде.

## ⚠️ Поправка по факту схемы (проверено на боевой БД, 2026-07-24)

Первоначальная гипотеза «геометрические зависимые (углы, люки, опоры, вводы)
переносятся по проекции точки» **оказалась неверной**: у этих таблиц колонка
`lineid` **всегда NULL** — они привязаны к сети **пространственно**, а не через FK.
Проверка `JOIN linesobj ON id=lineid` даёт 0 строк для всех геом.таблиц. Значит при
разрезании их переносить не нужно и нечего — принадлежность половине определяется
координатами при чтении.

**Реальная поверхность переноса** (у кого `lineid` действительно ссылается на `linesobj`):

| Класс | Таблицы | Резолвится к linesobj | Логика |
|---|---|---:|---|
| NODE (авто по узлу) | pressregulators, consumptregulators, pressdropregulators | 507 / 7 / 13 | переносится за своим `nodeid` |
| REVIEW (ручная проверка) | dampers, diaphragms, elevators, pumps, heatexchangers, systemradiators, airheaters | 12412 / 14140 / 2206 / 284 / 228 / 516 / 71 | реальный FK, но нет узла/позиции — **не угадываем** |

`heatpipesections` (паспорт 1:1) — клонируется отдельно. Геометрические таблицы из
карты переноса **исключены**. Итог: карта правил = 3 NODE + 7 REVIEW, все 10
SQL проходят `PREPARE` на боевой схеме.

Это **главный блокер отказа от Qt**: десктоп — редактор сети, web пока просмотрщик.
План закрывает изменяющую топологию часть с корректным переносом зависимых
объектов — технически самый рискованный узел всего перехода.

---

## 0. Цель и Definition of Done

Из браузера (авторизованно, на стенде) можно:
- создавать / перемещать / удалять узлы;
- создавать / удалять участки;
- **разрезать участок точкой** с корректным переносом всех зависимых объектов на нужную половину;
- отменять/повторять действия (undo/redo);
- всё — транзакционно, с аудитом, optimistic locking и возможностью «сухого прогона».

**Готово, когда:** контрольный набор из тестовой БД даёт после разрезания то же
распределение зависимых объектов, что и десктоп; ни один зависимый объект не «теряется»
и не остаётся на неправильной половине; операция полностью откатывается при ошибке.

## 1. Таксономия зависимостей — что именно переносить

Реальный масштаб (из схемы БД): **142 колонки-ссылки в 108 таблицах**
(`lineid` — 74 таблицы, `nodeid`/`nodeid1/2` — 57, плюс спец-поля). Из них
**заполнены данными** ~20 таблиц. Они делятся на **4 класса с разной логикой**:

### Класс 1 — Паспорт участка 1:1 (`heatpipesections`, 98 013)
Физический паспорт трубы, ровно один на линию. **Уже реализовано**: клонируется
для новой половины через `jsonb_populate_record` (без перечисления 150 колонок),
длины обеих половин пересчитываются. Оставить как есть, добавить тест.

### Класс 2 — Геометрические точечные объекты (есть `shape`)
Переносятся **по проекции точки на исходную геометрию**: доля вдоль линии
`< split_fraction` → остаётся на первой половине, иначе → на новой.

| Таблица | Записей | Смысл |
|---|---:|---|
| `ugol_povorota_truboprovoda` | 25 214 | Углы поворота |
| `lyuki` | 18 392 | Люки |
| `vvody_v_zdanie` / `vvod_v_zdanie` | 5 463 / 5 463 | Вводы в здание |
| `opora` | 3 611 | Опоры |
| `perehod_diametra`, `kapremont_uchastki_remonta`, `opressovka_defekt` | ед. | Прочее |

Правило (одно на все): пересчитать `ST_LineLocatePoint(orig_shape, obj.shape)`,
сравнить со `split_fraction`, при необходимости выставить `lineid = new_line_id`.

### Класс 3 — Оборудование без геометрии (привязка к узлу/месту установки)
Нет `shape` — позиционируется **семантически**: местом установки на узле или
признаком «в начале/в конце участка». Перенос: объект уходит на ту половину,
которая **сохраняет его узел установки**.

| Таблица | Записей | Поле места установки |
|---|---:|---|
| `diaphragms` | 16 718 | `throtdiaphloc` (место установки) |
| `dampers` | 14 868 | назначение/затвор |
| `elevators` | 2 754 | узел абонента |
| `systemradiators` | 622 | `location` |
| `pressregulators` / `consumptregulators` / `pressdropregulators` | 509 / 7 / 13 | регулируемый узел |
| `pumps` | 286 | узел станции |
| `heatexchangers` | 232 | `location` |
| `airheaters`, `localhydroresistances2` | 91 / 2 | — |

Правило (по типу): определить узел установки (nodeid1/nodeid2 исходной линии),
после разрезания nodeid1 остаётся у первой половины, nodeid2 — у новой; объект
следует за своим узлом. Для «вдоль участка» без узла — **флаг на ручное решение**.

### Класс 4 — Ссылки `nodeid` в 57 таблицах
При **создании узла** разрезания ничего не ломается (новый узел). Опасность — при
**удалении/слиянии** узла: 57 колонок `nodeid*` (журналы, оборудование, диагностика).
Правило удаления узла: запретить, если на узле висят зависимые записи, пока нет
явного правила переноса/каскада (safe-delete → soft-delete + проверка ссылок).

## 2. Алгоритм разрезания линии (целевой)

Внутри одной транзакции (расширяет текущий `split_line`):

```
1. fraction = ST_LineLocatePoint(orig.shape, click_point)   # уже есть
   guard: 1e-8 < fraction < 1 - 1e-8                          # уже есть
2. new_node = INSERT nodes (точка на fraction)                # уже есть
3. new_line = INSERT linesobj (new_node → nodeid2, substring f..1)  # уже есть
4. UPDATE orig_line SET nodeid2=new_node, shape=substring 0..f      # уже есть
5. heatpipesections: clone на new_line, пересчёт длин обеих           # уже есть
--- НОВОЕ ---
6. Класс 2 (геометрия): для каждой таблицы —
   UPDATE t SET lineid=new_line
   WHERE lineid=orig AND ST_LineLocatePoint(orig_shape, t.shape) >= fraction
7. Класс 3 (узел): для каждой таблицы по её правилу —
   объекты, чей узел установки = nodeid2, → lineid=new_line
8. Класс 4 не трогаем (nodeid стабильны)
9. Собрать отчёт перенесённых: {таблица: n} для аудита и UI
10. При ANY ошибке — ROLLBACK (savepoint на каждую таблицу)
```

Реализация классов 2/3 — **декларативной картой правил** (`SPLIT_TRANSFER_RULES`),
а не хардкодом на 20 таблиц: `{table, kind: 'geometry'|'node', node_field?}`.
Новую таблицу-зависимость добавляем строкой в карту.

**Dry-run:** параметр `dry_run=true` — выполнить в транзакции, вернуть отчёт
перенесённых объектов и **сделать ROLLBACK**. UI показывает «будет перенесено:
задвижек N, углов M…» до подтверждения.

## 3. Операции узлов и линий (полный набор редактора)

| Операция | Есть в API | Правило безопасности |
|---|---|---|
| Создать узел | ✅ (gated) | — |
| Переместить узел | ✅ (gated) | обновить геометрию инцидентных линий и их длины `heatpipesections` |
| Удалить узел | ✅ (gated) | **safe-delete**: запрет при висящих зависимостях (57 `nodeid`-колонок), иначе soft-delete |
| Создать линию | ✅ (gated) | нужен `heatpipesections` по умолчанию, savepoint на дочернюю вставку |
| Удалить линию | ✅ (gated) | перенести/осиротить зависимые по правилам класса 2/3 |
| **Разрезать линию** | ⚠️ частично | **раздел 2** — главный объём |
| Слить узлы (merge) | ❌ | будущее; сложнее split |

Перемещение узла сейчас двигает точку, но **не обновляет длину** участков и не
двигает геометрию линий — добавить в это же обновление.

## 4. Undo / redo

Десктоп имеет undo (`cxema/undo_gid.cpp`, 26 обращений) — пользователи этого ждут.

- **Серверный журнал операций** (уже есть таблица аудита): каждая мутация пишет
  «обратную» операцию (создан узел → undo = удалить узел; разрезание → undo =
  слияние + возврат lineid зависимых по сохранённому отчёту).
- Undo/redo — стек на сессию редактирования; применяется тем же
  транзакционным API. Разрезание откатывается по сохранённому `{таблица, id, old_lineid}`.
- MVP: undo только последней операции; полный стек — вторым шагом.

---

## 5. Безопасность и транзакционность

- **RBAC**: топология — роль `admin` (уже так в `require_topology_mutations_enabled`).
- **Флаги**: `TOPOLOGY_MUTATIONS_ENABLED` + `MUTATIONS_ENABLED` (уже есть) — включаем **только на стенде**.
- **Аудит**: каждая операция + отчёт перенесённых в `write_audit_log` (уже есть helper).
- **Optimistic locking**: версия/`archivechangedate` линии проверяется перед мутацией — если объект изменён другим пользователем, 409.
- **Транзакция + savepoints**: вся операция атомарна; на каждую таблицу-зависимость savepoint, чтобы одна битая строка не валила всё молча, а попадала в отчёт.
- **Allow-list таблиц** (уже есть) — карта правил переноса сверяется с реальной схемой при старте.

## 6. Тестирование и приёмка

1. **Тестовая БД** (копия с историей) — без неё приёмку не сделать (внешний блокер).
2. **Golden-тесты разрезания**: подобрать участки с реальными зависимостями каждого
   класса (углы, люки, опоры, вводы, задвижки, элеваторы, диафрагмы) и проверить,
   что после split распределение по половинам совпадает с десктопом.
3. **Property-тест**: сумма длин половин = длине исходной линии (±ε); ни один
   зависимый объект не потерян (count до = count после по обеим половинам).
4. **E2E**: клик по линии → dry-run отчёт → подтверждение → проверка на карте.
5. **Нагрузочный**: разрезание участка с максимумом зависимостей (углы/люки) не
   блокирует пул (`DB_COMMAND_TIMEOUT`).

## 8. Риски и снятие

| Риск | Снятие |
|---|---|
| Зависимый объект теряется/на неправильной половине | Property-тест count-до=count-после; dry-run превью |
| Класс 3 без узла установки — неоднозначность | Флаг на ручное решение оператора, не угадывать |
| Каскад при удалении узла (57 колонок) | Safe-delete: запрет при зависимостях, без «тихого» каскада |
| Расхождение с десктопом в правилах | Golden-тесты на контрольных участках, эталон — `cxema_edit`/SQL gid6 |
| Блокировка пула на тяжёлом участке | Транзакция + `DB_COMMAND_TIMEOUT`, индексы по `lineid` |
| Конкурентное редактирование | Optimistic locking (409), позже — блокировка участка на время правки |
